# 패키징 & 배포 준비

`npm run package` 로 웹스토어 업로드용 zip 을 만든다. 이 문서는 그 스크립트가 무엇을 보장하는지,
그리고 **실제 스토어 제출까지 아직 무엇이 비어 있는지**를 적는다.

> 이 문서는 스토어 등록 문구·개인정보처리방침을 대신 작성하지 않는다. 소유자가 직접 써야 하는
> 항목만 목록으로 정리한다.

## 1. 빌드

```powershell
npm install
npm run package
```

산출물: `dist/threads-clipper-v<version>.zip` (버전은 `manifest.json` 에서 읽는다).
`dist/` 와 `*.zip` 은 `.gitignore` 에 있으므로 산출물이 저장소에 커밋되지 않는다.

### 담기는 것

허용 목록 방식이다 — `scripts/package.js` 의 `INCLUDED_TOP_LEVEL` 에 나열된 것만 들어간다.

| 항목 | 비고 |
|---|---|
| `manifest.json` | |
| `src/` | 배경 스크립트, content script, 옵션 페이지 |
| `icons/` | 16 / 48 / 128 px |
| `assets/` | 지금은 없음. 생기면 자동 포함 |

현재 zip 내용은 14개 파일, 원본 48.7 KB → 압축 23.3 KB.

### 담기지 않는 것

`tests/`, `tests/fixtures/`, `docs/`, `scripts/`, `.github/`, `node_modules/`, `.git/`,
`package.json`, `package-lock.json`, `vitest.config.js`, `README.md`, `guide.md`, `STATUS.md`,
`CLAUDE.md`, 점(`.`)으로 시작하는 모든 파일, `Thumbs.db` 같은 OS 부산물.

> **제외 목록이 아니라 허용 목록인 이유**: 제외 목록은 새 폴더가 생길 때마다 조용히 새서
> 테스트나 내부 문서가 스토어에 올라간다. 허용 목록은 반대로 "빠지는" 쪽으로 실패하고,
> 그 실패는 매니페스트 참조 검증(아래)에서 바로 잡힌다.
> **최상위 폴더를 새로 추가하면 `scripts/package.js` 의 허용 목록도 같이 갱신해야 한다.**

### 재현 가능한 zip

아카이브 내부 타임스탬프를 1980-01-01 로 고정하고 항목을 경로순으로 정렬한다. 같은 소스면 항상
같은 바이트가 나오므로, 스크립트가 출력하는 `sha256` 값으로 "스토어에 올린 zip 이 이 커밋에서 나온
게 맞는지" 확인할 수 있다.

### 의존성

**추가된 의존성 없음.** zip 생성은 `scripts/zip.js` 에 직접 구현했고 Node 내장 `zlib` 의
`deflateRawSync` 만 쓴다(ZIP 압축 방식 8번이 곧 raw deflate). CRC-32 도 내장 테이블 구현이라
Node 버전을 타지 않는다. 확장 zip 은 수십 KB 규모라 ZIP64 가 필요 없고, 4GB·65535개를 넘으면
깨진 아카이브를 만드는 대신 예외를 던진다.

## 2. 테스트 게이트

**스크립트가 vitest 를 직접 실행하고, 실패하면 zip 을 만들지 않는다.** 우회 플래그는 두지 않았다.

"테스트를 돌렸는지 확인하고 안 돌렸으면 거부하는" 방식도 가능하지만 택하지 않았다. 그러려면
마지막 테스트 실행 시각을 파일에 남기고 소스 변경과 비교해야 하는데, 그 스탬프를 언제 무효화할지
정하는 순간 작은 빌드 시스템이 하나 더 생긴다. 게다가 스탬프는 **거짓말을 조용히 한다** — 테스트를
돌린 뒤 코드를 고치면 스탬프는 여전히 "통과"로 남는다. 직접 실행은 항상 지금 트리를 검증하고,
현재 전체 실행이 2~3초라 비용도 사실상 없다.

## 3. 빌드가 중단되는 조건

| 조건 | 결과 |
|---|---|
| `manifest.json` 없음 / JSON 파싱 실패 | 중단 |
| `version` 없음·빈 문자열 | 중단 |
| `version` 형식 오류 (`abc`, `1.2.3.4.5`, 앞자리 0 인 `01.2`, 65535 초과) | 중단 |
| 테스트 실패 | 중단 (`dist/` 자체를 만들지 않음) |
| 매니페스트가 참조하는 파일이 zip 에 없음 (service worker, content script, 옵션 페이지, 아이콘) | 중단 |

중단 시 종료 코드는 1 이고, 부분 산출물을 남기지 않는다.

경고(빌드는 진행)로 처리하는 것: `description` 누락·132자 초과, 아이콘 크기 누락, `LICENSE` 파일 없음.

## 4. 웹스토어 제출 준비 상태

### 이미 갖춘 것

- Manifest V3, `name` / `version` / `description`(50자, 상한 132자 이내)
- 아이콘 16 / 48 / 128 px 실제 존재 및 크기 확인 완료
- 원격 코드 실행 없음 (모든 스크립트가 패키지 안에 있음) — 심사에서 유리한 항목
- 단일 목적이 뚜렷함: "Threads 게시물을 로컬 Obsidian vault 에 저장"

### 소유자가 직접 준비해야 하는 것

**(a) 개발자 계정** — 1회 등록비 5 USD, 연락 이메일 인증, 계정 2단계 인증.

**(b) 스토어 등록정보** — 저장소에 없는 자산이다.
- 상세 설명 (스토어 페이지 본문)
- 스크린샷 최소 1장 — 1280×800 또는 640×400
- 스토어 아이콘 128×128 (`icons/icon128.png` 재사용 가능)
- 카테고리, 기본 언어
- (선택) 프로모 타일 440×280

**(c) 개인정보 보호 탭** — 항목별로 텍스트를 직접 써야 한다.
- 단일 목적 설명 (1~2문장)
- **권한별 사용 사유** — 아래는 코드 기준 사실 관계다. 문장은 소유자가 쓴다.

  | 권한 | 실제 쓰임 |
  |---|---|
  | `activeTab` | 단축키/아이콘 클릭 시 현재 Threads 탭에서 추출 실행 |
  | `storage` | 옵션(API 호스트·토큰·폴더·vault 이름) 저장 (`chrome.storage.sync`) |
  | `notifications` | 저장 성공/실패 데스크톱 알림, 클릭 시 노트 열기 |
  | `https://www.threads.com/*` | content script 주입 대상 (게시물·리포스트 페이지) |
  | `https://*.cdninstagram.com/*`, `https://*.fbcdn.net/*` | 본문 이미지·동영상 파일 다운로드 |
  | `http://127.0.0.1/*`, `https://127.0.0.1/*` | 로컬 Obsidian Local REST API 호출 |

- 원격 코드 사용: **아니오**
- 데이터 사용 공시 + 정책 준수 인증 체크박스

**(d) 개인정보처리방침 URL** — 이 확장은 사용자가 보고 있는 페이지 내용과 API 토큰을 다루므로
사실상 필수로 본다. **내용은 소유자가 직접 작성해야 한다.** 최소한 다음 사실이 담겨야 한다.
- 무엇을 읽는가: Threads 게시물 본문·이미지·동영상 URL
- 어디로 보내는가: 사용자가 설정한 로컬 Obsidian Local REST API 주소뿐. 개발자 서버로 가는 전송 없음
- 무엇을 저장하는가: API 토큰 등 설정값을 `chrome.storage.sync` 에 저장 → **구글 계정으로 동기화된다**
- 보관 기간·삭제 방법 (확장 삭제 시 설정도 제거)
- 문의 연락처

### 확인이 필요한 것

- 웹스토어 요건은 바뀐다. 제출 직전에 공식 문서로 다시 확인할 것.
- 아이콘 32px 는 권장 크기지만 `manifest.json` 에 없다(하드 차단은 아님).
- 로컬호스트 host permission 은 심사에서 설명을 요구받기 쉽다 — (c)의 사유를 구체적으로 쓸 것.
- Threads 콘텐츠를 수집·저장하는 동작이 해당 서비스 약관과 충돌하는지는 별도 판단이 필요하다.
  이 문서가 판단해 주지 않는다.

## 5. 라이선스 (미정 — 공개 배포 차단 항목)

현재 저장소에 `LICENSE` 파일이 없다. 라이선스가 없으면 기본 저작권이 적용되어 **제3자에게 사용·복제·
재배포 권한이 없다.**

정확히 하자면, 웹스토어 제출 양식 자체가 오픈소스 라이선스를 요구하지는 않는다. 그럼에도 공개 배포
전에 반드시 정해야 할 항목으로 본다.

1. 저장소가 공개돼 있고 zip 에 소스가 그대로 들어간다 — 받은 사람이 무엇을 해도 되는지 알 수 없다.
2. 개발자 약관상 배포 권한을 보증하게 되는데, 권리 관계를 문서로 남겨두지 않은 상태다.
3. 제3자가 포크해 다른 이름으로 재업로드해도 대응할 근거가 없다.

### 선택지

| 선택 | 한 줄 요약 |
|---|---|
| MIT | 가장 널리 쓰이는 허용적 라이선스. 저작권 고지만 유지하면 수정·상업적 이용·재배포 자유 |
| Apache-2.0 | MIT 수준으로 허용적이되 특허 사용 허가와 기여 조건이 명시됨 |
| MPL-2.0 | 파일 단위 카피레프트 — 수정한 파일만 같은 조건으로 공개하면 됨 |
| GPL-3.0 | 강한 카피레프트 — 파생물 전체를 같은 라이선스로 공개해야 함 |
| 독점 (All rights reserved) | 소스는 공개하되 사용 권한은 주지 않음. 배포 조건을 별도 문서로 명시해야 함 |
| 비공개 유지 | 스토어 배포를 포기하고 지금처럼 개발자 모드 로드로만 사용 |

**결정은 소유자 몫이다. 이 문서는 고르지 않는다.**

### 정한 뒤 할 일

1. 저장소 루트에 `LICENSE` 파일 추가
2. `README.md` 의 "라이선스" 섹션 갱신 (현재 "미정 (개인 용도)")
3. `package.json` 에 `"license"` 필드 추가
4. `npm run package` 의 LICENSE 경고가 사라지는지 확인
